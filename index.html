Hadoop

Understanding
Definition

Apache Hadoop is an open-source framework for distributed storage (HDFS) and distributed processing (MapReduce) of very large data sets across clusters of cheap commodity machines. It was created by Doug Cutting, based on Google's GFS and MapReduce papers.

Big Data: the 5 V's

  • Volume: huge size (TB to PB).
  • Velocity: data arrives fast (clicks, sensors, logs).
  • Variety: structured (tables), semi-structured (JSON, XML), unstructured (text, video).
  • Veracity: data may be noisy or uncertain.
  • Value: useful insight extracted from the data.

Core components

ComponentRole
HDFSStorage layer. Splits files into blocks and stores replicas across DataNodes.
YARNResource management and job scheduling (Hadoop 2+).
MapReduceProcessing model: Map → Shuffle & Sort → Reduce.
Hadoop CommonShared Java libraries and utilities used by all modules.

HDFS architecture (master–slave)

  • NameNode (master): stores metadata only: file names, directory tree, file → block mapping, and which DataNode holds each block. It holds no actual data. It is a single point of failure in Hadoop 1; Hadoop 2 adds a Standby NameNode for High Availability.
  • DataNode (slave): stores the actual blocks, sends a heartbeat every 3 s and a block report to the NameNode, and serves read/write requests.
  • Secondary NameNode: periodically merges fsimage + edit log (checkpointing). It is not a backup NameNode.
  • Block size: 128 MB by default (64 MB in Hadoop 1). Replication factor: 3 by default.
  • Rack awareness: 1st replica on the local node, 2nd and 3rd on a different rack, so the data survives a whole rack failing.
  • HDFS is write-once, read-many, built for large sequential reads.
Worked numeric example (commonly asked)

A 500 MB file with 128 MB blocks gives 128 + 128 + 128 + 116 = 4 blocks. With replication 3 that is 12 block copies, using 1500 MB of raw storage. The last block only uses 116 MB, because HDFS does not pad it.

HDFS write and read flow

Client asks NameNode→NameNode returns DataNode list→Client writes to DN1→DN1 → DN2 → DN3 pipeline→ACKs back
Client asks NameNode for block locations→Reads each block from the nearest DataNode directly

YARN (Yet Another Resource Negotiator)

  • ResourceManager (master, one per cluster): contains the Scheduler, which allocates resources, and the ApplicationsManager, which accepts jobs.
  • NodeManager (one per node): launches containers and reports their resource usage.
  • ApplicationMaster (one per job): negotiates resources from the RM and tracks its job's tasks.
  • Container: a bundle of CPU + memory in which a task runs.

Hadoop 1 had the JobTracker (master) and TaskTracker (slaves) doing both resource management and job tracking. YARN separated these so other engines like Spark can run on the same cluster.

Key features

  • Data locality: computation moves to where the data is, instead of moving the data.
  • Fault tolerance: replication and automatic re-execution of failed tasks.
  • Horizontal scalability: add more machines. Low cost: commodity hardware.

Limitations (why HBase and Spark exist)

  • Batch processing only. Data is accessed sequentially, so even a simple lookup scans the whole data set. HBase was built for random access.
  • MapReduce writes intermediate results to disk, which makes iterative jobs (ML, graphs) slow. Spark keeps data in memory.
  • Not real-time, and the small files problem: every file adds load to NameNode memory.

MapReduce: key, value

Understanding
Definition

MapReduce is a programming model for processing large data in parallel. Everything is a (key, value) pair.

Map: (k1, v1) → list(k2, v2)  ·  Reduce: (k2, list(v2)) → list(k3, v3)

Phases, in order

Input file→Input Splits→RecordReader→Map→Combiner (optional)→Partitioner→Shuffle & Sort→Reduce→Output (part-r-00000)
  1. Input split: logical chunk of input, usually one HDFS block. Number of mappers = number of splits.
  2. RecordReader: turns a split into key-value pairs. With TextInputFormat, key = byte offset of the line and value = the line.
  3. Mapper: runs your map logic on each record and emits intermediate (key, value) pairs. Its output goes to local disk, not HDFS.
  4. Combiner: a "mini reducer" that runs on the mapper's node to pre-aggregate and reduce network traffic. It is only safe for associative and commutative operations like sum, max and count. It is not safe for average.
  5. Partitioner: decides which reducer gets a key. The default is hash(key) mod numReducers, so all values of one key go to the same reducer.
  6. Shuffle & Sort: moves map output to reducers, groups values by key and sorts by key. This is where (k, v1), (k, v2) becomes (k, [v1, v2]).
  7. Reducer: aggregates each key's list of values and writes the final output to HDFS.

Example 3: Average marks per department (the combiner trap)

InputCSE,80 · CSE,90 · ECE,70 · CSE,70 · ECE,90

Why you can't use the reducer as a combiner for average

Suppose mapper 1 has CSE [80, 90], giving avg 85, and mapper 2 has CSE [70], giving avg 70. The average of the averages is 77.5, but the true average is 240 / 3 = 80. The fix is to emit (dept, (sum, count)) from the mapper or combiner, and divide only in the reducer.

Points to remember

  • The number of reducers is set by the user. With 0 reducers you get a map-only job: no shuffle, and mapper output goes straight to HDFS.
  • Reducers start only after all mappers finish. The shuffle copy can begin earlier.
  • Fault tolerance: if a task fails, it is re-run on another node using a replica of the block.
  • Speculative execution: a slow task is also launched on another node, and whichever copy finishes first wins.
  • Drawbacks: disk I/O between stages, so it is slow for iterative work, verbose to write, and batch-only.

Pig Latin

Code + output
Definition

Apache Pig is a high-level platform on Hadoop for analysing large data sets. Its language, Pig Latin, is a procedural data-flow language created at Yahoo. Every Pig script is converted internally into MapReduce jobs. About 10 lines of Pig can replace about 200 lines of Java MapReduce.

  • Execution modes: Local mode pig -x local (local files) and MapReduce mode pig or pig -x mapreduce (HDFS).
  • Ways to run: Grunt shell (interactive, grunt>), a script file (pig script.pig), or embedded (UDFs).
  • Internals: Parser → Optimizer → Compiler → MapReduce execution engine.
  • Statements are lazy. Nothing runs until DUMP or STORE.
  • Relation and field names are case-sensitive. Keywords like LOAD and FOREACH are not.
  • Fields can be referred to by position: $0, $1, …

Word count in Pig (very important)

Input /user/hadoop/HDFS_File.txt
hello world
hello pig
pig is fun
Pig Latin
lines     = LOAD '/user/hadoop/HDFS_File.txt' AS (line:chararray);
words     = FOREACH lines GENERATE FLATTEN(TOKENIZE(line)) AS word;
grouped   = GROUP words BY word;

DUMP wordcount;
Output
(fun,1)
(hello,2)
(is,1)
(pig,2)
(world,1)

How it works: TOKENIZE("hello world") gives the bag {(hello),(world)}. FLATTEN turns that bag into separate rows (hello), (world). GROUP and COUNT then do the same job as reduce in MapReduce.

Benefits of NoSQL

  • Handles large volumes of rapidly changing structured, semi-structured and unstructured data.
  • Fits agile development: quick schema iteration and frequent code pushes.
  • Geographically distributed scale-out architecture instead of an expensive monolithic server.
  • Dynamic schema: the structure can evolve as the data evolves. Example: a news Article first has Title, Author, Date and Category. Later you add Event, Location, Person and Claim without migrating the old records.
  • Auto-sharding: the database automatically splits data into shards and spreads them across servers. Benefits: scalability, performance, load balancing and automatic rebalancing. Example: 1 billion users are sharded by user_id into Shard 1 (0–333M), Shard 2 and Shard 3. When users grow, a 4th shard is created and the data is rebalanced.
  • Replication: copies of the data on several servers. A leader takes writes, replicas serve reads, giving high availability. Remember: sharding = dividing data, replication = copying data.

CAP theorem (Brewer's theorem)

Statement

A distributed system can guarantee only two of these three at the same time:

C – Consistency: every node sees the same data at the same time.
A – Availability: every request gets a response, even when some nodes fail.
P – Partition tolerance: the system keeps working even if the network between nodes breaks.

ClassGives upBehaviour during a partitionExamples
CPAvailabilityShuts down the inconsistent node until the partition healsHBase, MongoDB, Redis
APConsistencyAll nodes answer, but some may return old data. They resync laterCassandra, CouchDB, Riak, DynamoDB
CAPartition toleranceCan't tolerate a partition, so in practice it is a single-site / non-distributed systemMySQL, SQL Server, MariaDB (RDBMS)
  • Why CAP matters: it shows the trade-offs and the system's limits, and helps you choose the right database.
  • Choose consistency when transactions need strict accuracy, as in banking and finance.
  • Choose availability when the service must always respond, as in social media.

Types of consistency

  • Strong consistency: once an update completes, every later read returns the new value.
  • Weak consistency: no guarantee that later reads return the updated value.
  • Eventual consistency: if no new updates are made, all replicas eventually return the last value. Temporary inconsistency is allowed.

Variants of eventual consistency:

  • Causal: operations that are causally related are seen in the same order by every process. Useful for collaborative apps.
  • Sequential: all processes see operations in one common order.
  • Session: read-your-own-writes is guaranteed while the session lasts.
  • Monotonic read: once you have seen a value, you never see an older one. Monotonic write: writes by the same process are serialised in order.
  • Data-centric: data stays consistent across nodes regardless of concurrent operations.
Facebook example (eventual consistency)

Bob posts a story on Alice's wall and tells her to look. Alice checks and sees nothing. A minute later she checks again and the story is there. Facebook chose eventual consistency because it has over 1 billion users and huge write volume. Eventual consistency reduces load and improves availability.

HBase

Theory + shell code
Definition

HBase is an open-source, distributed, column-oriented NoSQL database built on top of HDFS. It is modelled on Google's BigTable, is horizontally scalable, and gives random, real-time read/write access to huge amounts of data. It uses HDFS for fault tolerance.

Why it's needed: Hadoop does only batch processing with sequential access, so even a simple lookup scans the whole data set. HBase lets you reach any row in a single unit of time (random access).

Use HBase when: the data is too large for an RDBMS, you need random real-time reads and writes, data is spread across many machines, the schema may change, and you need to scale horizontally.

Architecture: HMaster, RegionServer, ZooKeeper

HMaster

  • Assigns regions to RegionServers
  • Handles DDL: create, delete, modify tables
  • Monitors RegionServers and balances load
  • Handles failover. Backup HMasters stand by, but only 1 is active

RegionServer

  • Tables are split horizontally into Regions (row-key ranges, about 256 MB by default)
  • Serves client reads and writes
  • Runs on HDFS DataNodes
  • One server can hold up to about 1000 regions

ZooKeeper

  • The "traffic controller"
  • Stores the location of the META table
  • Tracks live servers through heartbeats and ephemeral nodes, and detects failures
  • Maintains configuration and provides distributed synchronisation

RegionServer components

ComponentRole
WAL (Write-Ahead Log)Log file on HDFS. Every write is recorded here first, so data is not lost if the server crashes
MemStore (write cache)In-memory buffer of new writes, sorted. One per column family per region
BlockCache (read cache)Keeps frequently read blocks in memory using LRU eviction
HFileThe file on HDFS where sorted key-values are stored permanently
RegionA row-key range of a table

How a client finds data (META lookup)

  1. The client gets the META table location from ZooKeeper.
  2. It asks META which RegionServer holds the row key, and caches the answer.
  3. It contacts that RegionServer directly for the row. Later requests use the cache, and META is asked again only on a miss, for example after a region moves.

Write path

1. Client write→2. WAL→3. MemStore→4. ACK to client→5. MemStore full: flush to HFile→6. Compaction

Read path

ZooKeeper / META→BlockCache→MemStore→HFiles on HDFS

Reads are fast because recent reads sit in the BlockCache and recent writes sit in the MemStore, so HBase often answers without touching disk.

Compaction and region split

  • Minor compaction: merges a few small HFiles into a bigger one with a merge sort. Saves space.
  • Major compaction: rewrites all HFiles of a region or column family into one, and drops deleted and expired cells. Improves read performance, but uses a lot of I/O.
  • Region split: when a region grows too large it splits into two daughter regions, each holding half the key range. The split is reported to the HMaster, which may move a daughter to another server for load balancing. Example: A001–Z999 splits into A001–M999 and N001–Z999.

Data model

  • Table: a collection of rows.
  • Row key: unique ID of a row, stored as bytes, with rows kept sorted lexicographically.
  • Column family: a group of related columns, defined when the table is created.
  • Column qualifier: an individual column inside a family, which can be added at any time. Written as family:qualifier.
  • Cell: the value at {row key + family + qualifier + timestamp}.
  • Version: a cell can keep multiple timestamped versions.
  • Data types: HBase is byte-oriented. Everything is stored as a byte array, and the application encodes and decodes strings, ints, floats, booleans, dates and binary data.

Advanced concepts

Row-key design

A good row key is unique, supports the most common queries, avoids concentrating writes in one region, is reasonably short, and keeps a useful order for range scans. Rows are stored sorted lexicographically: S001, S002, S003…

PatternExampleUse / problem
SequentialS001, S002, S003Easy direct lookups, but causes hotspotting because new rows always land at the end of the key range
CompositeCSE#S001, IT#S004When queries use more than one attribute (dept + id)
Reverse timestampC001#(Long.MAX_VALUE − ts)Latest records come first
Hash-basedA7#S001, B2#S002A hash prefix spreads writes across regions

Hotspotting

Too many reads or writes go to one region or RegionServer while the others sit idle. The effects are uneven writes, high load on one server, increased latency, poor cluster utilisation and lower overall performance.

Salting

Add a calculated prefix (salt) to the row key, for example hash(S001) % 10 giving 7#S001. Rows then spread across regions.

Bloom filter

A space-efficient probabilistic structure that tells whether a row may be in an HFile. Its answers are "definitely not present", so HBase skips that HFile, or "possibly present", so HBase reads the HFile. It never says "definitely present". Example: an HFile holds S001, S003, S005, S007. A request for S004 gets "definitely not", so that disk read is avoided.

Compression

Reduces disk space and disk I/O, which speeds up I/O-bound reads and writes. Codecs: NONE, GZIP, Snappy, LZ4, ZSTD.

Replication

Copies data from one HBase cluster to another, using the WAL to send changes to the peer cluster. It is used for disaster recovery, backup, availability and geo-distribution. Example: put 'student','S003',… on Cluster A shows up on Cluster B shortly after.

Recursive collection: ConsList

Scala
object SimpleConsList {
  sealed trait ConsList
  case object Empty extends ConsList
  case class Cons(head: Int, tail: ConsList) extends ConsList

  def sum(list: ConsList): Int = list match {
    case Empty => 0
    case Cons(head, tail) => head + sum(tail)
  }

  def main(args: Array[String]): Unit = {
    val numbers = Cons(10, Cons(20, Cons(30, Empty)))   // 10 → 20 → 30 → Empty
    println("Sum = " + sum(numbers))
  }
}
Output
Sum = 60

Trace: 10 + sum(20,30) = 10 + 20 + sum(30) = 10 + 20 + 30 + sum(Empty) = 10 + 20 + 30 + 0 = 60. It is recursive in two ways: the data structure contains itself (tail is a ConsList), and the function calls itself (sum(tail)). Scala's built-in List works the same way: 1 :: 2 :: Nil.

Tail recursion

In tail recursion, the recursive call is the last operation in the function. Scala applies Tail Call Optimisation, turning it into a loop with constant stack space, so there is no StackOverflowError. The @tailrec annotation makes the compiler raise an error if the call is not in tail position.

Normal recursion (NOT tail recursive)
def factorial(n: Int): Int =
  if (n == 0) 1 else n * factorial(n - 1)   // multiply happens AFTER the call
Tail-recursive factorial
import scala.annotation.tailrec

object TailRecursionExample {
  def factorial(n: Int): Int = {
    @tailrec
    def calculate(n: Int, result: Int): Int = {
      if (n == 0) result
      else calculate(n - 1, result * n)
    }
    calculate(n, 1)
  }
  def main(args: Array[String]): Unit = {
    val n = 5
    println("Factorial of " + n + " = " + factorial(n))
  }
}
Output
Factorial of 5 = 120

Accumulator trace: fact(5,1) → fact(4,5) → fact(3,20) → fact(2,60) → fact(1,120) → fact(0,120) → 120.

Apache Spark & PySpark

Theory + small program
Definition

Apache Spark is a fast, general-purpose distributed data-processing engine that keeps data in memory between steps. It is up to 100× faster than Hadoop MapReduce, which writes intermediate results to disk. It supports batch processing, interactive queries, streaming, machine learning and graph processing.

Features

  • Speed: in-memory DAG execution, up to 100× faster than MR.
  • Powerful caching: cache and persist to memory or disk.
  • Deployment: Standalone, Hadoop YARN, Mesos or Kubernetes.
  • Real-time: low latency thanks to in-memory computation.
  • Polyglot: Scala, Java, Python (PySpark), R and SQL. Shells: spark-shell (Scala) and pyspark (Python).

Two main abstractions

RDD: Resilient Distributed Dataset

  • Resilient: fault-tolerant. Lost partitions are recomputed from lineage, not from replicas.
  • Distributed: split into partitions across nodes and processed in parallel.
  • Dataset: a collection of records.
  • Immutable: never changed. Every operation creates a new RDD.
  • Two kinds of operations: transformations and actions.

DAG: Directed Acyclic Graph

  • The driver turns your program into a DAG of operations for each job.
  • Spark splits the DAG into stages at shuffle boundaries (wide transformations).
  • Narrow steps like map followed by filter are pipelined in one stage.
  • Spark optimises the whole graph before running it.
RDD partitions
RDD = [10,20,30,40,50,60]
Partition 1 → [10,20]     → Task 1
Partition 2 → [30,40]     → Task 2     (run in parallel)

Narrow transformation

Each output partition depends on one input partition, so there is no shuffle. Examples: map, filter, flatMap, union.

Wide transformation

An output partition needs data from many partitions, so there is a shuffle across the network and a new stage. Examples: groupByKey, reduceByKey, join, distinct, sortByKey.

Lazy evaluation: in rdd2 = rdd.filter(...), then rdd3 = rdd2.map(...), then rdd3.collect(), nothing runs until collect(). Spark then optimises and runs the whole plan together. The benefits are an optimised plan, fewer passes over the data, and no wasted computation.

reduceByKey vs groupByKey: reduceByKey combines locally first (like a MapReduce combiner) and then shuffles less data. groupByKey shuffles every value. Prefer reduceByKey for aggregations.

Q1. An e-commerce company has 2 TB of daily sales logs (region, product, amount). Find total sales per region. Which approach, and why?

Understanding: batch aggregation over very large data, grouped by region.

Tool: Spark, or MapReduce on Hadoop. The data is too big for one machine, and the aggregation is a simple key-value job. Spark is preferred for speed (in-memory) and less code.

Key-value design: Map emits (region, amount). Shuffle groups by region. Reduce sums. A combiner is safe because sum is associative.

PySpark · sample: South,500 / North,300 / South,200 / East,400 / North,100
sales = sc.textFile("sales.csv").map(lambda l: l.split(","))
total = sales.map(lambda r: (r[0], int(r[1]))).reduceByKey(lambda a, b: a + b)
print(total.sortBy(lambda x: x[1], ascending=False).collect())
Output
[('South', 700), ('North', 400), ('East', 400)]
ConclusionSouth has the highest sales (700). Spark's reduceByKey combines values locally before the shuffle, so it handles 2 TB efficiently. Spark is recommended over MapReduce for repeated daily runs.

Q2. A bank and a social media app both need a database. Using the CAP theorem, which type should each choose?

Understanding: a network partition is unavoidable in a distributed system, so each must choose between C and A.

Bank: wrong balances are unacceptable, so choose CP (e.g. HBase, MongoDB) or an ACID RDBMS. It is better to reject a request during a partition than return stale data.

Social media: must always respond, and a few seconds of stale likes or posts is acceptable, so choose AP (e.g. Cassandra, DynamoDB) with eventual consistency and the BASE properties. The Facebook wall example shows exactly this.

ConclusionThe bank needs consistency (CP/ACID) and social media needs availability (AP/BASE). No single choice is best everywhere, because CAP forces a trade-off based on what the business can tolerate.

Q3. Design an HBase table for IoT sensors writing readings every second. Reads ask for "latest readings of sensor X".

Understanding: very heavy writes plus time-ordered reads per sensor.

Problem: a row key like timestamp or a sequential key makes every write hit the last region, which is hotspotting.

Design: row key = salt#sensorId#reverseTimestamp, where salt = hash(sensorId) % 10 spreads the writes and the reverse timestamp puts the latest reading first. Column families: data (temp, humidity) and meta (location). Enable a Bloom filter and Snappy compression.

HBase shell
create 'sensor', {NAME => 'data', VERSIONS => 1, COMPRESSION => 'SNAPPY', BLOOMFILTER => 'ROW'}, 'meta'
put 'sensor', '3#S17#9223370278800000000', 'data:temp', '31.5'
scan 'sensor', {FILTER => "PrefixFilter('3#S17#')", LIMIT => 1}
Output
ROW                         COLUMN+CELL
 3#S17#9223370278800000000  column=data:temp, timestamp=..., value=31.5
1 row(s)
ConclusionSalting removes write hotspots, and the reverse timestamp makes "latest reading" a single short prefix scan. HBase is suitable because it gives random real-time access on HDFS at a scale an RDBMS can't handle.

Q4. Using Pig, find the number of employees in each city and identify the city with the most employees.

emp.txt: 1,Arun,Chennai / 2,Priya,Madurai / 3,Ravi,Chennai / 4,Divya,Kochi / 5,Meena,Chennai
emp  = LOAD 'emp.txt' USING PigStorage(',') AS (id:int, name:chararray, city:chararray);
g    = GROUP emp BY city;
cnt  = FOREACH g GENERATE group AS city, COUNT(emp) AS total;
srt  = ORDER cnt BY total DESC;
top1 = LIMIT srt 1;
DUMP srt;
DUMP top1;
Output
(Chennai,3)
(Kochi,1)
(Madurai,1)

(Chennai,3)
ConclusionChennai has the most employees (3 of 5, 60%). Pig did this in 6 lines, where Java MapReduce would need far more code, because GROUP + COUNT does the shuffle and reduce internally.

Q5. A data science team runs a machine-learning algorithm that loops over the same data 50 times. Should they use MapReduce or Spark?

Analysis: MapReduce writes to HDFS after every job, so 50 iterations means 50 rounds of disk reads and writes. Spark can cache() the data set in memory once and reuse it in every iteration. Lineage still gives fault tolerance.

PySpark sketch
data = sc.textFile("points.txt").map(parse).cache()   # read once, keep in RAM
for i in range(50):
    w = data.map(lambda p: gradient(p, w)).reduce(lambda a, b: a + b)
ConclusionSpark is the better choice, often 10–100× faster for iterative workloads, because cached RDDs avoid repeated disk I/O. MapReduce suits only simple one-pass batch jobs.
